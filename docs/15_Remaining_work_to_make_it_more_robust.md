# 더 견고해지기 위해 남은 작업

여기서 추가로 더 견고한 결제 시스템을 구축하는 데 필요한 나머지 작업들에 대해 알아보자.

## Security

- **Request/response eavesdropping:**
    - **피해**: 데이터가 전송 중에 노출되서 민감한 정보가 유출될 수 있다. (e.g 고객의 신용카드 번호나 개인정보)
    - **해결 방법**: HTTPS 를 사용해서 통신을 암호화함으로써 데이터를 보호할 수 있다.
- **Data tampering:**
    - **피해**: 데이터 변조는 거래의 세부 사항을 변경하여 결제 금액을 조작하거나 다른 상품으로 변경하는 등의 피해를 입힐 수 있다.
    - **해결 방법**: 데이터 전송 시 암호화뿐만 아니라 무결성을 검사하는 시스템을 구현해서 데이터가 변경되지 않았는지 확인해야한다.
- **Man-in-the-middle attack:**
    - **피해**: 공격자가 통신을 중간에서 가로채서 데이터를 열람하거나 조작하는 것. 이를 통해 고객과 서비스 제공자간의 신뢰가 깨질 수 있다.
    - **해결 방법**: SSL(Secure Sockets Layer)를 사용해서 통신을 암호화하고, 인증서 피닝(Pinning)을 통해 인증서가 타당한지 확인해야한다.
- **Data loss:**
    - **피해**: 데이터베이스에 문제가 생겨 데이터를 잃을 경우, 거래 기록의 손실로 이어져 법적 책임이나 고객의 불신을 초래할 수 있다.
    - **해결 방법**: 데이터베이스를 여러 지역에 복제하고, 주기적으로 데이터 스냅샷을 취해서 복구할 수 있는 방안을 마련해야한다.
- **Distributed denial-of-service attack (DDoS)**:
    - **피해**: 서비스가 과도한 트래픽으로 사용 불가능하게 되면, 실제 고객이 서비스를 이용할 수 없게 된다.
    - **해결 방법**: Rate limiting, 방화벽과 같은 기능을 통해 비정상적인 트래픽의 유입을 차단해야한다.
- **Card theft**:
    - **피해**: 카드 번호 도용은 무단 거래를 가능하게 한다.
    - **해결 방법**: 실제 카드 번호 대신에 토큰을 사용해서 저장하고 결제에 사용함으로써, 실제 카드 번호가 노출되지 않도록 한다.
- **PCI compliance**:
    - **피해**: PCI DSS 기준을 준수하지 않으면 신용카드 정보의 유출 가능성이 높아지고, 이로 인해 법적 문제와 과태료 부과의 위험이 있다.
    - **해결 방법**: PCI DSS 는 신용카드 정보를 안전하게 처리, 저장, 전송하기 위한 엄격한 규정을 제공하니 이 규정을 따르면 된다.
- **Fraud**:
    - **피해**: 사기 피해는 부정 거래를 통해 재정적 손실을 입힐 수 있다. 이는 가짜 거래나 도난당한카드의 사용 등이 있다.
    - **해결 방법**: 주소 검증 서비스 (AVS), 카드 검증 값(CVV) 확인, 사용자 행동 분석 등을 통해서 거래의 유효성을 검사해야한다. 이러한 조취들로 인해서 실제 카드 소유자가 거래를 진행하고 있음을 보증하고, 이상 행동이나 일관성 없는 거래 패턴을 감지할 때 추가적인 인증을 요구할 수 있다.

## 부하 테스트

이 말은 많은 시스템이 설계 단계에서는 우수해 보일 수 있으나, 실제 대규모의 트래픽 상황에서는 예상치 못한 문제에 직면할 수 있다는 뜻이다.  
따라서 부하 테스트를 통해 시스템이 실제 운영 환경에서 예상되는 트래픽을 원활하게 처리할 수 있는지 확인해야한다.

부하 테스트는 시스템이 최대 사용량 조건에서도 안정적으로 작동할 수 있는지를 평가하는 과정이다. 이 테스트는 다음과 같은 이유로 필수적이다:

- 성능 병목 현상 식별: 시스템의 성능을 저하시키는 병목 현상을 사전에 식별할 수 있다.
- 시스템 한계 파악: 시스템이 안정적으로 처리할 수 있는 최대 트래픽 수준을 파악함으로써, 예상치 못한 트래픽 증가 시 대응 방안을 마련할 수 있다.
- 사용자 경험 보장: 부하 상황에서 결제가 되지 않으면 고객 만족도에 직접적인 타격을 줄 수 있으므로, 해당 테스트는 필요하다.
- 비용 절감: 성능 문제를 사전에 발견하지 못하고 운영 환경에 배포하는 경우 문제를 해결하기 위한 비용이 크게 증가될 수 있기 때문에 부하테스트는 필요하다.

를 통해서 시스템이 고부하 상황에서 어떻게 반응하는지 확인해봄으로써 병목이 발생하는 영역을 파악할 수 있다.

이런 문제를 사전에 발견하지 못하고 실제 운영 환경에 배포하는 경우, 문제를 해결하기 위한 비용이 크게 증가할 수 있다. (e.g 시스템 개선, Downtime, UX 저하 등)

## Monitoring

주요 모니터링 지표를 기반으로 대시보드를 만들어서, 실시간으로 모니터링하고 알람을 보내서 문제를 신속하게 해결하는 것이 중요하다.

### 어플리케이션 지표:

- **헬스 정보**: 어플리케이션이 정상적으로 자동할 수 있는 상태인지 알려주는 여부
- **응답 시간**: 각 서비스의 평균 및 최대 응답 시간.
- **처리량**: 초당 요청 수(Transactions Per Second, TPS)와 같은 시스템의 처리 능력.
- **오류율**: 각 서비스의 오류율 및 예외 발생 비율.
- **JVM 메트릭**: Heap, GC, 스레드, 로드 및 언로드 된 클래스 정보 등
- **시스템 메트릭:** CPU Utilization, File Descriptor 등 ****
- **서버 엔진 메트릭**: Netty, Tomcat

### 데이터베이스 지표:

- **쿼리 성능**: 가장 시간이 많이 걸리는 쿼리와 가장 자주 실행되는 쿼리의 성능 지표 (e.g 실행 시간, 실행 빈도 등)
- **커넥션 풀**: 사용 가능한 커넥션 수, 활성 커넥션 수, 유휴 커넥션 수.
- **복제 지연**: 데이터 복제 지연 시간
- **CPU Utilization**: 데이터베이스 인스턴스의 CPU 사용률
- **Slow query log**: 지정된 시간보다 더 길게 되는 쿼리 로그
- **DML Latency**: 데이터를 삽입(INSERT), 갱신(UPDATE), 삭제(DELETE) 하는 데 걸리는 시간
- **Select Latency**: SELECT 쿼리의 실행 시간
- **Commit Latency**: 트랜잭션이 커밋되는 데 걸리는 시간
- **Buffer Cache hit Ratio**: 버퍼 캐시에서 요청한 데이터를 찾는 비율
- **Blocked Transaction**: 다른 트랜잭션으로 인해 블로킹되고 있는 트랜잭션의 수
- **Rollback Segment History Length**: 트랜잭션이 롤백될 때, 롤백 작업을 처리하기 위해 보관해야 하는 히스토리의 양
- **Threads_running**: 데이터베이스에서 현재 실행 중인 쿼리 수를 말하며, 이 지표가 빠르게 증가하고 감소되는 식으로 변화하지 않는다면 쿼리가 신속하게 완료되지 않는다는 의미다.
- **I/O Utilization**: I/O 대기 시간이 길다는 건, 점점 더 디스크에서 데이터를 가져와서 처리하므로 성능이 점점 느려지고 있다는 뜻이다.

### 카프카 모니터링:

- **메시지 레이턴시**: 메시지가 생성되고 소비될 때까지의 각 지연 시간.
- **처리량**: 초당 전송된 메시지 수, 브로커별로 초당 메시지 건 수, 초당 들어오고 나가는 바이트 수
- **요청/응답 큐 크기**: 해당 큐의 크기가 크다는 건 처리되지 못하고 있는 요청/응답이 많다는 뜻이다.
- **Lag 매트릭**: Consumer 가 처리해야 할 메시지 양을 나타내는 지표.
- **Isr Shrink ParSec**: 브로커가 다운된다거나, 리플리케이션 동작에 문제가 있는지 확인할 때 사용되는 지표
- **RequestHandlerAvgIdlePercent**: 요청 핸들러 스레드가 유휴 상태인 평균 시간을 나타낸다. 이 값이 0이면 모든 리소스가 사용된 것이다.
- **NetworkProcessorAvgIdlePercent**: 네트워크 프로세서 스레드가 유휴 상태인 평균 시간을 나타낸다. 이또한 이 값이 0이면 모든 리소스가 사용된 것이다.
- **record-error-rate**: 이 지표 값이 0이 아니라면 프로듀서가 보내고 있는 메시지에는 유실이 발생하고 있다는 뜻이다.
- **request-latency-avg**: 이 지표는 브로커에서 쓰기 요청이 받을 때까지 걸리는 평균 시간이다. 이 값이 평상시보다 높다면 쓰기 요청이 점점 느려지게 처리되고 있다는 뜻으로 브로커에 문제가 발생한 것일 수 있다.
- **byte-consumed-rate**, **records-consumed-rate**: 컨슈머가 얼마나 많은 메시지 트래픽을 처리하고 있는지 나타내는 지표
- **sync-time-avg**, **sync-rate**: 컨슈머 코디네이터가 동기화 작업에 들어간 평균 시간을 나타내는 sync-time-ave 와 초당 그룹 동기화 수를 나타내는 sync-rate 를 통해서 동기화가 얼마나 자주 일어나는지 보여줄 수 있다. 컨슈머 그룹이 안정적이라면 이 두 값의 경우 모두 0일 것이다.
- **commit-latency-avg**: 오프셋 커밋하는데 걸리는 평균 시간
- **assigned-partitions**: 특정 컨슈머 어플리케이션에 할당된 파티션 수

### 외부 서비스 의존성 모니터링:

- **외부 서비스 호출 성능**: 외부 API 호출의 응답 시간 및 오류율
- 외부 PG사 장애 에러 모니터링 (케이스 위주):
    - 고객이 결제를 진행까지 많이 하는데 외부 PG사나 은행의 문제로 결제 실패율이 올라가는 경우
    - 동일한 에러 메시지가 일정 비중 이상 반복되는 경우
    - 고객이 결제 시도는 많이 하는데 실제로 처리되는 결제 승인 비중이 떨어지는 경우

## 외부 PG사 장애 조치

- 외부 PG사에서 장애 알람을 받을 수 있도록 구축
- 문제가 되는 결제 수단을 차단해서, 결제 문제를 방지하기.
- 결제는 실패했지만 돈만 빠져나가는 문제가 발생한 경우에 빠르게 해결하는 배치 서비스 구축
- 장애가 발생하더라도 이를 견디기 위해 여러 PG사 다중화

## Durability

내구성(Durability)이란 어떠한 상황이라도 데이터가 안전하게 보존되어야 함을 의미한다.  
결제 시스템의 내구성을 강화하는 방법에 대해 알아보자.

### Replication

복제는 내구성(Durability) 와 가용성(Availability) 를 높이는 핵심 전략이다.  
복제를 통해 결제 시스템의 데이터를 여러 서버나 위치에 분산해서 저장함으로써,  
단일 지점 장애(Single Point of Failure) 를 방지하고 데이터 손실 없이 시스템 서비스를 계속해서 제공할 수 있다.

### Backup

데이터 복제만으로는 모든 데이터 손실 시나리오에 대비할 수 없기 때문에 정기적인 데이터 백업은 필수적이다.

백업 전략은 다음과 같다:

- 전체 백업(Full Backup): 시스템의 모든 데이터를 특정 시점에 저장하는 전략이다. 데이터 복원 시간을 최소화할 수 있지만, 저장 공간과 백업 시간이 많이 필요하다.
- 증분 백업(Incremental Backup): 마지막 전체 백업 이후 변경된 데이터만 백업하는 방식이다. 저장 공간과 시간을 절약할 수 있으나 데이터 복원 과정이 복잡하다.
- 차등 백업(Differential Backup): 마지막 전체 백업 이후 변경된 모든 데이터를 백업하는 것을 말한다. 증분 백업보다는 복원이 간단하지만, 시간이 지남에 따라 더 많은 저장 공간을 요구한다.

## Reliability

여기서는 시스템의 신뢰성을 향상 시킬 수 있는 방법들에 대해 더 알아보자.

### Circuit Breaker

Circuit Breaker 패턴은 시스템의 일부가 실패했을 때, 전체 시스템이 실패하는 것을 방지하기 위한 패턴이다. 
결제 시스템은 다양한 외부 서비스와 통신해야 하는 경우가 많다. 
이러한 외부 시스템과의 통신 중에 장애가 발생한다면 전체 결제 처리 과정이 지연되거나 실패할 수 있다. 
Circuit Breaker 패턴을 적용함으로써, 결제 시스템은 이러한 외부 시스템의 장애로부터 스스로를 보호할 수 있게 된다.

Circuit Breaker 패턴의 주요 매커니즘은 다음 세 가지 상태(Closed, Open, Half-Open)의 변화를 통해 알 수 있다:

- **Closed 상태**: 정상적인 상태에서 Circuit Breaker 의 상태를 나타낸다. 이 상태에서는 모든 요청이 외부 서비스로 전달된다. 만약 정해진 기준(e.g 실패율, 타임아웃)을 초과하는 오류가 발생한다면 Circuit Breaker 는 Open 상태로 전환된다.
- **Open 상태**: Circuit Breaker 가 Open 상태가 되면, 외부 서비스로의 모든 요청이 차단된다. 이는 실패한 외부 서비스가 회복될 시간을 확보하고, 추가적인 부하로 인한 시스템의 오버로드를 방지할 수 있다. Open 상태는 사전에 정의된 타임아웃 동안 지속된다.
- **Half-Open 상태**: Open 상태의 타임아웃이 경과된 후, Circuit Breaker 는 Half-Open 상태로 전환된다. 이 상태에서는 제한된 수의 테스트 요청을 외부 서비스로 전달해서 서비스의 상태를 점검한다. 테스트 요청이 성공하면 시스템이 정상으로 복구된 것으로 간주하고, Circuit Breaker 를 다시 Closed 상태로 되돌린다. 만약 실패한다면, Circuit Breaker 는 다시 Open 상태로 돌아간다.

### Graceful Shutdown

Graceful Shutdown 은 시스템이 예상치 못한 장애로 인해 종료될 때 처리를 마무리하고 종료되도록 만드는 과정이다.  이렇게 진행 중인 작업을 안전하게 마무리하고 리소스를 해제함으로써 데이터 손상을 방지할 수 있다.

어플리케이션은 다양한 이유로 종료될 수 있다. (e.g 어플리케이션 배포, 예기치 못한 장애로 인한 긴급 재시작 등) 따라서 Graceful Shutdown 기능이 필요할 수 있다.

### Clustering

데이터베이스의 안정성과 가용성을 보장하기 위해서 클러스터링 기능은 중요하다. 데이터베이스 클러스터링은 여러 데이터베이스 서버를 그룹화해서 하나의 단일 시스템처럼 작동하도록 만드는 기능이다.

클러스터링 기능을 통해 클러스터 내의 모든 서버는 지속적으로 데이터를 동기화 하고, 하나의 서버에 문제가 발생하더라도 다른 서버가 작업을 인계받아 시스템은 지속적으로 작동될 것이다.
